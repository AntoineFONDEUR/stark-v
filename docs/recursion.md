# Recursive proving

## Terminology and crate boundary

`continuation` and `recursion` solve different problems:

- `continuation` proves every execution segment independently and verifies all
  resulting proofs on the host. It also checks that adjacent public machine
  states match. A run with `n` segments produces `n` proofs, and both proof
  bytes and verification work grow with `n`. This is not recursion.
- `recursion` defines a universal AIR with a segment-leaf branch and a binary
  node branch. A completed binary tree will replace two child proofs with one
  proof of the same protocol and shape. Only this path can produce one
  constant-size root proof.

The recursion crate has no version suffix. Its root modules are the only active
recursion design.

## Current status

The recursive verifier is not finished and the repository does not currently
expose a recursive prover, recursive verifier, tree builder, or root-proof API.
No code should describe the project as already producing a constant-size root
proof.

The implemented foundation includes:

- a canonical protocol manifest and fixed-width proof wire;
- typed complete-execution, job, slot, executed-span, and empty-span statements;
- a fixed verifier control plan shared by native transcript execution and AIR
  tables;
- canonical transcript recording, payload ownership, digest-state chaining,
  proof-of-work checks, and relation-challenge binding;
- VM public-claim decoding and hashing;
- statement semantics for segment leaves, empty leaves, and binary folds;
- VM AIR composition evaluation generated from the prover component roster;
- DEEP quotient, trace-Merkle, FRI-Merkle, FRI-fold, last-layer, and query
  position constraints;
- an AIR self-program for verifying a recursion child;
- shared QM31 multiplication, inversion, linear-operation, and Merkle-path trace
  tables;
- component, malformed-witness, relation-closure, and leaf-binding tests.

The missing integration is substantial: the existing components are not yet
assembled into a complete universal trace, committed by an outer prover, or
verified through a public root API. In particular, a real recursion proof cannot
yet be used as a binary child.

The live universal roster has 36 components. Poseidon2 is generated by
`define_air_fns!`, and `range_check_8_8` comes from `define_air!`; the other 34
components still have hand-written `FrameworkEval` implementations, usually
backed by `define_component_tables!`. Those 34 are migration debt. They must be
migrated before new recursion integration work; passing their current component
tests does not waive that requirement.

The host continuation remains useful while recursion is incomplete, but it is
not a final statement-verification API. Its public data does not currently bind
segment roles, and its verifier does not accept an application-supplied
complete-execution statement. Callers must not treat those helpers as a
constant-size or fully statement-bound proof system.

## Recursive statement

`CompleteExecutionStatement` is the application claim. It binds:

- protocol identity;
- program digest;
- initial and final machine state;
- public input and output digests;
- total cycle count.

`JobContext` adds the prover-internal segment count and derives the unique
minimal binary-tree height. `SpanStatement` binds one exact slot range inside
that tree. An executed span carries its first segment, number of segments, first
cycle, number of cycles, entry and exit state, and optional input/output edge
claims. An empty span has one canonical representation.

A valid binary node has two adjacent children of equal height. They must share
one job, occupy the exact left and right child slots, and agree at their
machine-state boundary. Folding them yields the unique parent span. Padding is
represented by canonical empty leaves, not by omitted children or proof-selected
tree shapes.

## Universal verifier

The proof kind selects one of three branches:

- `SegmentLeaf`: verify one stark-v VM proof and derive its height-zero
  statement;
- `BinaryNode`: verify two proofs produced by this recursion AIR and fold their
  statements;
- `EmptyLeaf`: prove the canonical unused slot required to complete the tree.

The protocol manifest fixes PCS parameters and the exact proof shapes for the VM
and recursion lanes. `VerifierControlPlan` derives the mandatory verifier
schedule from that trusted manifest. Proof bytes supply values only; they do not
choose operation counts, transcript phases, Merkle depths, FRI widths, or
relation closures.

The universal relation registry fixes relation draw order. The VM relation
bundle comes first so shared VM components preserve their established challenge
layout. Recursion-local relations then connect control, transcript, statement,
arithmetic, query, Merkle, DEEP, and FRI tables. The final proof must enforce
global LogUp closure across the complete roster.

## Soundness invariants

The finished system must preserve all of these properties:

- The verifier schedule is derived from a trusted manifest and cannot be
  shortened or reordered by proof bytes.
- Every wire integer and field word has one canonical encoding; inactive
  fixed-capacity slots are all zero.
- The transcript absorbs the protocol, statement, PCS parameters, commitments,
  claims, sampled values, FRI data, and proof-of-work nonces in the same order
  as the native verifier.
- Every VM or recursion AIR constraint contributes to the composition value.
- Every opened value is bound to an authenticated trace or FRI path.
- Every public LogUp term is accumulated, and the global relation sum is zero.
- A segment leaf binds the VM public claim to exactly one height-zero span.
- A binary node verifies both children, checks adjacency, and exposes only the
  unique folded parent statement.
- Empty leaves can only pad slots beyond the declared segment count.
- The root statement equals the application-supplied complete-execution
  statement.
- Recursive proof shape and root verification work are independent of the number
  of segment leaves supported by the fixed protocol profile.

## Finish-line task list

The tasks below are dependency ordered. A task is complete only when its
acceptance criteria pass in release mode and malformed-witness tests cover the
new binding.

1. Normalize the live 36-component roster on the accepted macro DSL.
   - Keep `poseidon2` (`define_air_fns!`) and `range_check_8_8` (`define_air!`).
     Migrate the other 34 components with no exceptions.
   - Migrate shared primitives first: `qm31_mul`, `qm31_inv`, `linear_ops`, and
     `merkle_path`.
   - Migrate trusted control tables next: `control`, `vm_public_logup_control`,
     and `vm_air_composition_control`.
   - Migrate the transcript family: `transcript_air`, `transcript_binding`,
     `transcript_state`, `transcript_word`, `transcript_payload`, `pow_check`,
     `pow_frame`, `relation_challenge`, and `verifier_randomness`.
   - Migrate statement and VM-public-input adapters: `statement_input`,
     `statement_semantics_input`, `vm_public_claim_input`,
     `vm_public_claim_hash`, `vm_public_io_hash`,
     `vm_public_claim_semantics_input`, `vm_public_logup_input`, and
     `vm_air_composition_input`.
   - Migrate the PCS family last: `query_bits`, `query_mapping`, `merkle_root`,
     `trace_merkle`, `pcs_deep_input`, `fri_merkle_leaf`, `fri_merkle_node`,
     `fri_merkle_anchor`, `fri_verifier_control`, and `fri_verifier_input`.
   - Rewrite every direct `define_component_tables!` declaration and every
     hand-written `FrameworkEval` implementation through `define_air!` or
     `define_air_fns!`.
   - Extend `define_air!` or `define_air_fns!` when a required expression,
     relation, mask, or witness operation is not representable; do not preserve
     a manual component as an exception.
   - Generate columns, constraints, witness filling, relation registration,
     interaction traces, component claims, and composition evaluation from the
     same macro definition.
   - Add a repository guard that fails if an active recursion component uses
     `define_component_tables!` or implements `FrameworkEval` outside generated
     code.
   - Acceptance: the recursion dependency graph contains only
     `define_air!`/`define_air_fns!` components, generated layouts match their
     witnesses, and focused release tests pass after each migrated family.

2. Freeze the supported protocol profile.
   - Select the VM PCS parameters, recursion PCS parameters, maximum table
     sizes, proof shapes, FRI layer capacities, and query count used by the
     first supported profile.
   - Derive every manifest field from the actual VM and recursion component
     rosters; do not copy sizing constants from probes or documentation.
   - Pin the protocol identifier and preprocessing column identifiers with
     conformance vectors.
   - Acceptance: native encoding and AIR encoding produce the same manifest
     digest, and changing any manifest field changes the protocol identity or
     fails validation.

3. Add the real VM-proof adapter.
   - Convert `prover::Proof<Poseidon2M31Hash>` and its public data into the
     fixed `SegmentProofWire` representation.
   - Derive the leaf `SpanStatement` from the verified public claim, segment
     index, cycle interval, and job context.
   - Reject values that exceed fixed capacities, non-canonical optional roots,
     and any mismatch between runner metadata and proof public data.
   - Acceptance: a real segment proof round-trips through the wire; one test per
     malformed field proves rejection.

4. Build one universal trace assembler.
   - Introduce a single witness container for every component in the universal
     roster, including shared arithmetic, Poseidon2, Merkle path, and byte-range
     tables.
   - Execute the trusted control plan to populate transcript, statement,
     public-claim, randomness, PCS, FRI, and circuit-lowering tables.
   - Derive component log sizes from populated tables and pad each table with
     its constrained inactive representation.
   - Acceptance: assembling the same verifier input twice produces identical
     claims, log sizes, preprocessed identifiers, and traces.

5. Close the segment-leaf verifier end to end.
   - Feed a real VM proof through transcript replay, VM public-claim semantics,
     VM AIR composition, trace openings, DEEP quotient evaluation, FRI, and
     last-layer checks.
   - Add all verifier-owned public terms and generate every interaction trace.
   - Enforce zero global LogUp sum across the whole universal roster.
   - Acceptance: a valid VM proof satisfies every universal component; a
     mutation in each proof region or skipped control phase fails one focused
     test.

6. Close the empty-leaf branch.
   - Emit the canonical statement and the minimal trace required for an empty
     slot.
   - Constrain emptiness to slots at or beyond the declared segment count and
     below the fixed tree capacity.
   - Acceptance: canonical padding verifies, while an empty proof in an executed
     slot or a non-zero inactive wire fails.

7. Implement the outer recursion prover and verifier foundation.
   - Preprocess the universal AIR for the frozen protocol profile.
   - Define the recursion proof bundle with only the public protocol identity,
     parent statement, component claims, interaction claims, and STWO proof.
   - Prove and verify the complete universal roster with the Poseidon2-M31
     channel.
   - Make the verifier accept an expected protocol and expected parent
     statement; never return success without comparing both.
   - Acceptance: one segment-leaf proof and one empty-leaf proof verify, and
     every public claim or proof mutation is rejected.

8. Close the recursion-child verifier end to end.
   - Encode the real proof emitted by task 7 into the recursion-child wire and
     bind it to its child statement and protocol.
   - Replay its transcript using the recursion control plan and the recursion
     AIR self-program.
   - Verify its claimed sums, composition value, trace openings, DEEP quotient,
     FRI layers, proof of work, and final polynomial.
   - Acceptance: one real recursion proof from task 7 closes all relations as a
     child; changing any child statement, commitment, opening, claimed sum, or
     FRI value fails verification.

9. Assemble and prove the binary-node branch.
   - Materialize two complete recursion-verifier lanes under the left and right
     verifier identifiers using two proofs emitted by task 7.
   - Prove equal child heights, exact slot adjacency, shared job identity,
     boundary state equality, edge-claim placement, and the unique parent fold.
   - Keep child witnesses independent; no tuple may be exchangeable between
     lanes without its verifier identifier.
   - Feed the completed binary witness through the outer prover and verifier
     from task 7.
   - Acceptance: valid adjacent child proofs yield one verified parent proof
     with exactly the native folded statement; swapped, duplicated, gapped,
     overlapping, or mismatched children fail focused tests.

10. Implement one binary-tree driver.
    - Segment a run, prove VM leaves, append canonical empty leaves to the
      unique minimal power-of-two capacity, and prove successive binary levels.
    - Allow parallel work only within a level; a parent starts after both child
      proofs and statements are available.
    - Return one root proof and its `CompleteExecutionStatement`, not a vector
      of descendant proofs.
    - Acceptance: runs with 1, 2, 3, 4, and 8 executed segments all produce one
      root proof with the expected statement.

11. Add the application-facing root API.
    - Accept the expected program, initial state, final state, public input,
      public output, total cycles, and protocol identity from the caller.
    - Verify one root proof and compare its root span to that complete execution
      claim.
    - Keep continuation APIs in the `continuation` crate and recursive APIs in
      the `recursion` crate; do not add compatibility aliases that blur them.
    - Acceptance: the correct application statement verifies, and one focused
      test rejects each mismatched statement field.

12. Prove the constant-size property.
    - Serialize root proofs produced from different supported segment counts
      under the same frozen profile.
    - Record proof bytes and root-verifier work independently from prover tree
      work.
    - Acceptance: every supported segment count yields exactly one proof of the
      same serialized size and the same root-verifier operation shape.

13. Complete adversarial and end-to-end coverage.
    - Add negative tests for non-canonical wires, transcript reordering, omitted
      relation challenges, wrong Merkle directions, reused paths, altered OODS
      samples, incorrect FRI positions, non-zero relation sums, bad padding,
      boundary discontinuities, and statement substitution.
    - Run focused package tests first, then previous failures, then the full
      workspace suite and repository hooks, all in release mode where the tool
      supports it.
    - Acceptance: unit, integration, end-to-end, conformance, full-workspace,
      and pre-commit checks pass with no ignored soundness test.

14. Publish only measured claims.
    - Measure proof size, peak memory, leaf proving throughput, per-level node
      proving time, and root verification time on the frozen profile.
    - Update the README and this document from those results and remove any
      temporary probes or superseded audit snapshots.
    - Acceptance: every performance or size claim names its profile and is
      reproducible from a checked-in benchmark or test.

## Finish-line definition

The project reaches the recursion finish line only when an application can
submit one expected complete-execution statement and one root proof, the root
verifier checks that statement without descendant proofs, and the serialized
proof size is unchanged across the supported segment counts of the frozen
profile. Passing component tests alone is not completion.
